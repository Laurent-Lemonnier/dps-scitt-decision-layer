## what the text says (read before changing anything)
# draft-gilda-audit-agent-audit-record-03, Section 5.9: "consumption MUST carry each of these members and no other (vector CS9):
# limitDigest, unit, limit, consumed, reserved, requested, held, stateRevision"; held entries carry "that permit's operationKey,
# requestDigest and amount". No payee, no settled, no x402 in -03; none of the four codes (consumption-key-reused is a corpus name
# too). Section 5.9 of -02 and -03 differ only by the sentence on CS7/CS17 ("puts no condition on when the held permit was issued").
# So the verifier's reading of CS43 to CS49 as consumption-malformed on the first pass was the letter of -03, not a bug against -03.
# The members come from the corpus README (0.35.0, "Consumption state and the operation key: CS1 to CS49"), which writes CS41 to
# CS49 as "rows written for revision 04" (no -04 is published: ietf.org/archive/id/...-04.txt answers 404 on 7 November), beside
# its other rules outside the text that the verifier already implements from that README (CS18 to CS40, X1 to X18):
#   "consumption.payee, and payee on each held entry, is the SHA-256 digest of the payee's CAIP-10 account id [...]. A retry pays
#   the held entry's payee (CS41); a payment signed again to another payee inside one call carries the same operation key and
#   request digest, and is consumption-key-reused (CS42). consumption.settled carries exactly amount, asset, payee, source and
#   transaction: the terms the call settled on, read from the chain through the transaction the server returned (source of chain),
#   beside the approved terms that requested, asset and payee carry from the signed payment. An x402 upto permit that settles below
#   its authorized maximum is valid (CS43); a settled amount above requested is consumption-settled-exceeds (CS44), another asset
#   or payee is consumption-settled-differs (CS45, CS46), and terms read from the signed payload are consumption-value-invalid
#   (CS47). consumed takes the settled amount, so the rest of the hold stays available: a later record of the ledger that no
#   longer holds the call counts at least the consumed the settling record read plus the settled amount (CS48), and one that
#   counts less is consumption-set-settled-uncounted (CS49). It may count more, since other calls can settle between the two."
## what changed in the verifier (from that text alone; the reference reader's code was not opened)
# - consumption may carry payee and settled (was: consumption-malformed); held entries may carry payee (was: consumption-malformed, X6)
# - payee (entry and held) = 64-hex digest else consumption-value-invalid; the CAIP-10 account id is not in the record, so only
#   the form is checked (the digests of P and Q in the vectors do equal SHA-256 of "eip155:84532:<EIP-55 address>", checked by hand)
# - settled: exactly the five members (consumption-malformed), amount non-negative integer, asset of the CAIP-19 shape, payee a
#   digest, transaction a non-empty string (consumption-value-invalid), source must be "chain" (consumption-value-invalid, CS47);
#   then amount > requested = consumption-settled-exceeds (CS44); asset != consumption.asset or payee != consumption.payee =
#   consumption-settled-differs (CS45, CS46), absent counting as different
# - retry (own key held) whose held entry names a payee: consumption.payee must equal it, else consumption-key-reused (CS42)
# - set check per ledger: every later record not holding the settling record's key counts consumed >= that record's consumed +
#   settled.amount, else consumption-set-settled-uncounted (CS48 valid at 37 USDC, CS49 malformed at 35)
# - withinLimit unchanged (the hold is requested; CS43 at 42 of 50 USDC); nothing ties settled to effect.observed (the README does not)
# Readings where the README leaves a choice are listed in the file's docstring (07/11/2026 paragraph); none is settled by a vector.
